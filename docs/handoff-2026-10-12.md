## Goal

Make dvdst a tool that agents reach for when asked to analyze coding-agent
sessions, and that they can extend, instead of parsing session JSONL by hand.

The work started from evidence. In the `omakase-v2` sessions, agents used
dvdst almost only for `stage`. When told to use it for analysis, one agent
guessed a wrong entry point, ran `files` once, and wrote its own Node scripts
over the raw sessions.

## What exists now

Row commands read session files directly, need no store, and write JSONL:

| command | one row per |
| --- | --- |
| `dvdst overview` | session |
| `dvdst turns` | model request |
| `dvdst calls` | tool call joined to its result |
| `dvdst context` | system prompt section |
| `dvdst schema [stream]` | prints every field |
| `dvdst rows <name\|file>` | runs a project extractor |
| `dvdst cache [--clear]` | shows or empties the row cache |

A session is a file, an id or id prefix, a filename timestamp prefix,
`latest`, or `$PI_SESSION_FILE`. `--last`, `--since`, `--root`, `--project`,
and `--source pi|claude|all` select several.

### Rules the code holds itself to

- Every emitted row key must be in `STREAMS`. A test enforces it. Add the
  field to the table when you add it to a row.
- Every command, flag, and field the skill names must exist. A test enforces
  it. A prose line in the skill must not start with `dvdst <word>` unless the
  word is a command.
- Derived output states what it is. Bash effects are `confidence: inferred`.
  Null means the source does not record the value, never zero.
- A logic change that alters derived store output bumps the extractor version.
  Current versions: classifier 3, artifact extractor 3, event extractor 2,
  bash parser 2.
- The row cache invalidates on the size and mtime of five source files listed
  in `ROW_LOGIC` in `src/analysis/cache.ts`. Add a file there if its logic
  decides rows.
- Tests run with `DVDST_CACHE=off`. The cache test sets its own directory.
- Docs follow the repository's writing lint: no semicolons, no em dashes, no
  contractions, active voice.

## Evidence that it works

Two fresh agents were given a question in `omakase-v2` that did not mention
dvdst, twice each: before and after the cache and sequence fields.

| run | tool calls | time | cost | behavior |
| --- | --- | --- | --- | --- |
| Claude Code, first | 7 | 57 s | not recorded | loaded the skill, copied rows to `/tmp` |
| Claude Code, second | 6 | 52 s | not recorded | queried dvdst directly, used `verbs` and `classes` |
| Pi (deepseek-v4.1-flash), first | 34 | 140 s | $0.018 | loaded the skill, copied rows to `/tmp`, bucketed with `awk` |
| Pi, second | 38 | 164 s | $0.025 | 36 direct dvdst calls, 14 used the sequence fields |

Both agents loaded the skill unprompted, ran `dvdst schema` before filtering,
and never read a raw session file. Spot checks of their headline numbers
against dvdst matched.

To repeat a run:

```bash
cd ~/Projects/omakase-v2
pi -p "Look at the last 30 Pi sessions in this project and tell me where agents are wasting the most effort. Give me the top 3 findings, each with the evidence behind it. This is analysis only: do not change any files."
dvdst calls latest | jq -r '[.seq, .tool, .isError, (.command // .path // "")[0:150]] | @tsv'
```

## Open work, in suggested order

1. **Failures hidden inside calls that exit 0.** Both Claude Code runs had to
   search result text for `FAIL` lines by hand, because a loop or pipe hides
   the exit code. dvdst knows only the status of the whole call. A project
   rule could name result patterns, for example `resultMarkers` in
   `.dvdst/config.json` with a name and a regular expression, counted per
   call into a field. Result text is not in cached rows, so the count must be
   derived before caching.
2. **Field selection.** Two Pi calls returned about 51 KB each, at Pi's output
   limit, because whole rows carry long command text. Add `--fields a,b,c`,
   and consider a width limit for `command`.
3. **Marking analysis sessions.** The Pi agent had to exclude its own analysis
   sessions by hand. Options: an `--exclude <id>` flag, or a project rule that
   tags sessions by first prompt or by use of dvdst.
4. **Store merge.** This is the main structural gap. Two systems exist: the
   row commands, and the store pipeline (`ingest`, `normalize`, `artifacts`,
   `events`) that produces findings. They differ in paths, arguments, and
   field names (`textBytes` against `outputBytes` in `src/cli/records.ts`).
   The store takes Pi sessions only, so Claude Code sessions have no findings.
   Neither test agent touched `events`. The plan: refactor the three
   extractors (`src/normalize`, `src/artifacts`, `src/events`) into pure
   functions over parsed records, serve findings as a row stream, and reduce
   `src/probe/build-bundle.ts` to the same functions. `files`, `commands`, and
   the handoff's "Read files" list still ignore bash reads because they run on
   the bundle path.

Smaller known issues:

- One malformed line skips the whole session. This can hit a session that is
  still being written, including the one the agent runs in.
- `dvdst sessions` lists Pi files only.
- The CLI starts three nested Node processes, which sets a floor near 0.3 s.
- `timeline` reads live stores only. Its ENOENT on a Pi store, seen in old
  session logs, was not re-tested.
- `scripts/run-benchmark.mjs` was not re-run. It rewrites the report in
  `docs/`. The handoff text changed (`created` and `candidates` commits), so
  run it and review the diff before a release.
- Subagent sidechain entries of Claude Code sessions are left out.

## Decisions already made

- Branch from `master` instead of committing to it. The owner accepted this.
- Commit only when the owner says so. Each step so far was committed on an
  explicit request.
- `latest`, `--last`, and `--since` select Pi sessions by default. An id is
  looked up across both agents.
- Extractors load from the directory dvdst runs in, or `DVDST_EXTRACTORS`, and
  never from a directory a session recorded, because they are code that runs.
- `rereads` is conservative: the read tool with the same offset and limit, or
  a whole-file bash read such as `cat`. A search or a line range does not
  count.
- The `file-modified-without-observed-read` finding keeps firing for a write
  that creates a file. It now carries `operation`, so a consumer can keep
  edits only.
